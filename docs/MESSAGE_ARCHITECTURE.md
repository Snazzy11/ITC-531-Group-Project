# Architecture

## How it works

Requests go through the gateway to the API. RabbitMQ holds messages until a
worker picks them up. The API publishes image jobs, matching jobs, item events,
`match.confirmed` and `request.failed`. The matching worker publishes
`match.potential_found` and the image worker publishes `image.processed`.

```text
Client -> gateway (localhost:8000) -> API (internal port 8000)

Functions in app/messaging.py
  RabbitMQ default exchange ("")
        jobs.item_matcher -> matching_worker
        jobs.image_processor -> image_worker
  seekr.events (topic exchange)
        # -> events.logger -> logger -> eventlogs volume
        match.potential_found / match.confirmed
              -> events.notifier -> notifier

RabbitMQ stores its data in the brokerdata volume.
```

## Job queues

Each job goes through the default exchange. Its routing key is the queue name.

- `publish_matching_job` sends `{"item_id": 42}` to `jobs.item_matcher`, which is both the queue name and routing key. `matching_worker` reads from this queue. The API sends it when an item is posted (`POST /items`) or goes back to `open` (`PATCH /items/{item_id}/status`, or an unmatch with `DELETE /matches/{match_id}`), and once for a demo item when demo data is seeded. Those are best-effort like events: if the broker is down the API logs a warning and the request still succeeds. Admins can queue one by hand with `POST /items/{item_id}/match-search`, which returns 202, or 503 if the job could not be queued.
- `publish_image_job` sends `{"item_id": 42, "image_ref": "<upload_id>"}` to `jobs.image_processor`, which is both the queue name and routing key. The API sends it from `POST /items/{item_id}/images/{upload_id}/complete`. `image_worker` reads from this queue.

Both workers check the message and acknowledge it when they are done. An
acknowledgment tells RabbitMQ it can remove the message. `matching_worker` scores
the item against every `open` item of the other type (lost against found), keeps
the 5 best in the `potential_matches` table in place of the item's earlier
suggestions, and publishes `match.potential_found` for each pair it had not
suggested before. An item that is gone or no longer `open` is skipped. Users see
the suggestions with `GET /items/{item_id}/potential-matches`. `image_worker` checks and
re-encodes the upload and records the result in Postgres (see
`milestones/milestone4/STORAGE_DESIGN.md`). A rejected upload is still acknowledged, since retrying it
would give the same result.

Item IDs must be positive integers. `image_ref` must be a string that is not empty
or just spaces.

## Events

`publish_event` checks the event and sends it to the `seekr.events` topic exchange.
The event type is also its routing key.

Every event has these fields:

- `event_id`: a UUID generated by the publisher.
- `schema_version`: currently 1.
- `timestamp`: the time the event was built, in UTC.
- `source`: the name of the service sending it.
- `event_type`: one of the seven types below.
- `payload`: the information for that event.

- `item.created`: payload fields are `item_id`. Sent to `events.logger`.
- `item.updated`: payload fields are `item_id`. Sent to `events.logger`.
- `item.withdrawn`: payload fields are `item_id`. Sent to `events.logger`.
- `match.potential_found`: payload fields are `lost_item_id`, `found_item_id`, `score`. Sent to `events.logger`, `events.notifier`.
- `match.confirmed`: payload fields are `match_id`, `lost_item_id`, `found_item_id`. Sent to `events.logger`, `events.notifier`.
- `image.processed`: payload fields are `item_id`, `upload_id`, `status` (`ready` or `rejected`), and `reject_reason` for a rejected upload. Sent to `events.logger`.
- `request.failed`: payload fields are `request_id`, `method`, `path`, `status` (500-599), `code` (the error code the client got) and `error_type` (the exception's class name). Sent to `events.logger`. The exception message and traceback stay in the API's console log, found by `request_id`, because they can include SQL or bucket details.

The API publishes `item.created`, `item.updated`, and `item.withdrawn` after the
change is saved, `match.confirmed` after `POST /matches` saves a match, and
`request.failed` after it has sent any 5xx response. The matching worker
publishes `match.potential_found` and the image worker publishes
`image.processed` (with `source` set to `matching-worker` and `image-worker`).
All of this is best-effort: if the broker is down, the publisher logs a warning
and carries on, so an event can be lost.

All payload IDs must be positive integers. The score cannot be negative and has
no upper limit; higher means more words in common.
The source cannot be blank, and extra fields are rejected. The models are in
`app/events.py`. Each event also has a version 1 JSON schema in `events/`.

The `logger` reads from `events.logger`. Its `#` binding means it receives all
events. It saves them to `/app/logs/events.jsonl` in the `eventlogs` volume and
acknowledges after the write is saved to disk. Each line is
`{"routing_key": ..., "event": {...}}`. To watch it:

```sh
docker compose --env-file .env.local exec logger tail -f /app/logs/events.jsonl
```

At startup the logger checks that it can write the file and exits with
`Cannot write /app/logs/events.jsonl` if not. That usually means the
`eventlogs` volume was created by an older image that ran as root; `docker
compose down --volumes` recreates it. The API declares the logger's and
notifier's queues when it starts, so events sent before those services first
run wait in the queue instead of being dropped. `scripts/smoke_test.sh` posts an
item and checks that its `item.created` line reaches the file.

The `notifier` reads from `events.notifier`. It has a binding for each of the two
match event types. It logs "Would notify" and then acknowledges. It does not send
notifications yet. Separate queues let both subscribers receive the same match
event.

## Message handling

All workers and subscribers use `prefetch_count=1`. This gives each one a single
message at a time, so it does not hold other messages while busy.

The queues and topic exchange use `durable=True`, and messages use
`delivery_mode=2`. These settings, along with the `brokerdata` volume, are meant
to keep queued messages through a broker restart.
Publishers wait for broker confirmation and report an error if a message cannot
be routed. The calling code receives publishing errors.

For both job queues and all event types, messages that fail the handler's checks
are rejected and discarded. The event subscribers only check that the message
is a JSON object the publisher checks the full event schema.

If a worker loses its connection before acknowledging, RabbitMQ puts the message
back on the queue. Another consumer can then receive it. An unexpected handler
error stops the process and closes its connection. Workers do not restart
automatically.
