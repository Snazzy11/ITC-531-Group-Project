# Storage design

We store two kinds of object:

- **Item photos.** The client uploads straight to the store with a presigned
  PUT, and `image_worker` checks and re-encodes the upload. The API never
  handles the bytes.
- **User files.** Proof of ownership a user keeps on hand for claiming an item,
  such as a receipt or a photo of a serial number. These go through the API
  (`/files`), which checks each file before writing anything.

Code: `app/ports/storage.py` (the only module that talks to the store),
`app/files.py` (file endpoints), `app/api.py` (photo endpoints),
`app/image_worker.py` and `app/image_processing.py` (photo checks and
re-encoding). The diagram is `architecture-diagram.png`.

Every item photo is re-encoded to the app's fixed resolution (a JPEG, at most
1280px on its longest side). Each item has at most one; a new upload replaces
it. This is a destructive process, and once the new photo is written, the
original upload is erased. In a real app we would want a thumbnail size, and a
high resolution photo for inspection. This is a good balance for us, for now.

Every id that names an object is a UUID generated by our code.

## Photo upload flow

1. `POST /items/{item_id}/images` creates an `images` row (`awaiting_upload`)
   and returns an `upload_id` and a presigned `upload_url`, valid 10 minutes.
2. The client PUTs the file to `upload_url`. The bytes go straight to the
   store and never pass through the gateway or the API.
3. `POST /items/{item_id}/images/{upload_id}/complete`. The API checks that the
   object exists, queues the image job, and sets the row to `processing`.
   Nothing is queued until the client calls this.
4. The image worker checks the upload (below), writes the re-encoded photo, and
   sets the row to `ready`, or `rejected` with a `reject_reason`. It then
   deletes the item's previous photo and the pending upload.
5. Item responses carry `photo_url`, a presigned GET valid for 1 hour.
   `GET /items/{item_id}/images/{upload_id}` shows the status of one upload.

```shell
API=http://localhost:8000/api/v1
UPLOAD=$(curl -s -X POST $API/items/1/images)
curl -s -X PUT --upload-file photo.jpg "$(echo "$UPLOAD" | jq -r .upload_url)"
curl -s -X POST "$API/items/1/images/$(echo "$UPLOAD" | jq -r .upload_id)/complete"
```

## Key templates

```
uploads/pending/{upload_id}                 # a raw photo upload, before checks
items/{item_id}/{upload_id}/photo.jpg       # the re-encoded photo
users/{user_id}/files/{upload_id}.{ext}     # a file uploaded through /files
```

- **`uploads/pending/`** - Prefix for staging photos. A presigned PUT would
  otherwise let unvalidated bytes go straight into a key we serve. By staging
  them, content-type checking stays involved without making every byte go
  through our API. Nothing reads this prefix except the image worker, and only
  once.
- **`items/`** - Prefix on the permanent photo. Lets you list or delete every
  object belonging to one item (`items/{item_id}/`), which is what we need for
  cleanups. What this gives up: we can't cheaply list "every photo a user ever
  uploaded" by using the bucket; it has to go through `Item.user_id` in
  Postgres first. Per-item walking is the common case, and bulk per-user
  listing is rare.
- **`users/{user_id}/`** - Prefix on user files, user first because "what proof
  do I have on file" is the question a claim asks, and it becomes one list call.
  What this gives up: "every PDF uploaded this week" means listing every user's
  prefix. That question is answered by the `files` table instead, which has
  `content_type` and `uploaded_at` columns and is what `GET /files` filters.
- **`{item_id}`** - scopes the photo to the row that references it.
- **`{upload_id}`** (the server-generated UUID, never the filename) - a
  duplicate upload gets a fresh key instead of overwriting the old one in
  place, so the worker can delete the old photo only after the new one is
  confirmed written. Filenames never appear in a key, so they can't reveal
  anything or collide. The original filename lives in the `files` table and in
  the object's `original-name` metadata.
- **`.jpg`** - fixed, because the worker always re-encodes to JPEG. The pending
  key has no extension at all: nothing about the upload is known or trusted
  until the worker checks it.
- **`.{ext}`** on files - chosen by our code from the type detected in the
  bytes (`pdf`, `jpg`, `png`, `webp`, `heic`), not taken from the filename.

Two users upload `resume.pdf` through `POST /files`. The keys differ in the
user and the UUID, neither of which the users chose, and `resume.pdf` appears
in neither, so the second upload cannot replace the first:

```
users/17/files/3f1c9e0a-6b2d-4c71-9a55-0d8e7f1b2c34.pdf
users/42/files/b7a4d2e8-1c93-4f06-8e2a-5c6d9b0f3a11.pdf
```

(A PDF could not be an item photo; the image worker would reject it.)

## Content types

To determine content type we use `file -k`, on the actual bytes, ignoring
the `Content-Type` header and the filename extension. Both can be manipulated
by attackers, and both can simply be wrong. With no arguments, the `file`
command stops at the first rule that matches. Using `-k` keeps on reading the
file after that and reports every rule satisfied. We do that because a
"polyglot upload" can be used as an attack too: bytes that are simultaneously
a valid image and a valid JavaScript document can smuggle a script past a naive
first-match check. Every match has to fall inside the allow-list, or the
upload is refused before it can be stored. (Every file also matches a generic
`application/octet-stream` rule, which says nothing about the bytes, so that
line is ignored.)

`file -k` only catches a polyglot whose second format it recognizes. It also
looks for most formats only at the start of the file. Data appended after a
valid image, such as a PNG followed by a ZIP or an HTML page, passes the check.
For photos, the re-encode below is what removes it: the stored photo is a new
JPEG built from the decoded pixels, so nothing after the image survives.

**Photos.** The allow-list is images, with reasonable flexibility on formats
(jpeg, png, gif, bmp, webp, heic/heif). The re-encode uses Pillow, limited to
decoders for those same formats. Writing a fresh JPEG also drops EXIF metadata,
including the GPS location most phone photos have. Uploads over 15 MB or 50
megapixels are rejected.

**Files.** The allow-list is JPEG, PNG, WebP, HEIC and PDF; anything else is a
`400` and anything over 10 MB is a `413`, both before a byte is written. Files
are stored as uploaded, with the detected type as the object's content type
and the `files` row's `content_type`. Downloads add `Content-Disposition:
attachment` and `X-Content-Type-Options: nosniff`.

**The dangerous one: `image/svg+xml`.** SVG _is_ an image format, but it is
stored XML, so it can embed `<script>`. Served back from a presigned URL, the
browser renders it as a page and runs that script (`text/html` is the same
problem). Neither allow-list contains either type, so an SVG photo upload is
rejected, and what we store for every photo is `image/jpeg` produced by the
re-encode, never the type the client sent.

## Bucket layout

| Prefix | Written by | Read by |
|---|---|---|
| `uploads/pending/{upload_id}` | Client, by PUT to the presigned `upload_url` | Image worker, once; erased by the worker whether the upload is stored or rejected |
| `items/{item_id}/{upload_id}/photo.jpg` | Image worker, after `file -k` passes and the image is decoded and resized | Client, by GET to the presigned `photo_url` on item responses. Deleted when a newer photo replaces it or the item is hard-deleted |
| `users/{user_id}/files/{upload_id}.{ext}` | API, `POST /files` and `POST /files/batch`, after the size and type checks | API, `GET /files/{id}/content`. Deleted by `DELETE /files/{id}` |

The bucket is private. Every client read or write goes through the API or a
presigned URL, and no presigned GET is ever made for `uploads/pending/`. Every
object our code writes carries `upload-id` metadata; only a client's presigned
PUT produces an object without it, which is how `scripts/storage_report.py`
spots one left behind.

## Write order

There is no transaction across Postgres and the store, so every path writes in
the order that makes a partial failure leave an **object with no row**, never a
row pointing at nothing. `POST /files` writes the object first and the row
second (and tries to delete the objects if the row fails); `DELETE /files/{id}`
and the item hard delete remove the row first and the objects second; the
image worker writes the new photo before marking its row `ready`, and deletes
the old photo only after that commit. An orphan object costs storage but is
invisible to users, and the storage report finds it. An orphan row would hand
out a URL that returns an error. The one row written ahead of its object is
the `awaiting_upload` row created when a photo upload link is issued; it is a
pending record that never produces a URL, and an upload that never arrives
leaves exactly that row.

## Presigned flows

**Bytes through the API.** For a photo, the API handles two small JSON
exchanges (the upload link, then `/complete`), and 0 bytes of the photo
itself; `evidence/presigned.txt` shows the PUT going to the store's port, not
the gateway's.

**Expiry.**

- *PUT, 10 minutes.* The link is requested at the moment the user picks a photo,
  and a phone photo under our 15 MB limit uploads in seconds. A short window
  limits a leaked link to a few minutes of writing one object into a staging
  prefix that the worker checks anyway.
- *GET, 1 hour.* A fresh `photo_url` is minted on every item response, so
  replacing an expired one costs a single refetch. An hour covers a browsing
  session while bounding how long a forwarded link keeps working.

**An expired URL.** The store answers an expired URL with `403` and an XML
error body. We have no front end yet, so this is the behaviour the client must
implement, and the API is built to support it: on a failed image load, the
client refetches `GET /items/{id}` for a new `photo_url` and, if that also
fails, shows "Photo unavailable. Refresh to try again." On a failed PUT, it
asks `POST /items/{id}/images` for a new link and retries once, then shows
"Your upload link expired. Please choose the photo again." The XML is never
shown.

**Reconciliation.** We implemented the completion callback:
`POST /items/{item_id}/images/{upload_id}/complete` checks that the object
exists before queueing the job. It does not cover a client that uploads and
never calls `/complete`, such as a closed tab: the API never learns of the
upload, the object sits in `uploads/pending/`, and the row stays
`awaiting_upload`. The lifecycle rule in `COST_AND_RISK.md` expires that prefix
after a day, and the storage report lists any it finds; a sweep that expires
the stale rows would be the next thing to build.

**The signed hostname.** Inside Docker the app reaches the store at
`http://storage:9000`, which a browser cannot resolve, and the hostname is part
of the signature, so rewriting it afterwards breaks the URL. The storage port
keeps two clients: every call the app makes goes to `S3_ENDPOINT_URL`, and
presigned URLs are signed against `S3_PUBLIC_ENDPOINT_URL`
(`http://localhost:9000` locally), the address the client will use. Signing is
local and makes no network call, so the app never needs to reach that address
itself. Against a provider, both are the same public endpoint and
`S3_PUBLIC_ENDPOINT_URL` is left unset.

## Emptying a versioned bucket

On a versioned bucket, deleting an object does not remove any bytes: it adds a
delete marker on top, and every earlier version is still stored and billed.
`list_objects_v2` only shows current versions, so once everything is "deleted"
it returns nothing and the bucket looks empty, but deleting the bucket fails
because the old versions and delete markers are still in it. That is why
`empty_bucket()` in `app/ports/storage.py` pages `list_object_versions` and
deletes every version and every delete marker by version id. If it used
`list_objects_v2` instead, a Module 8 teardown would report success while
every photo we ever replaced was still stored and billed, the bucket delete
would fail, and the leftover versions would keep costing money after the
course ended.
