
# Part 1 Answers

### 1.1 Key scheme

Uploaded documents: `users/{user_id}/uploads/{YYYY}/{MM}/{DD}/{uuid}.{ext}`
Generated exports: `users/{user_id}/exports/{YYYY}/{MM}/{DD}/{uuid}.{ext}`

Components:
- `users/`: a fixed top-level prefix, so everything user-owned lists separately from anything else in the bucket.
- `{user_id}`: first on purpose. It is the most common filter ("show me my files"), and a prefix is the only query the store has.
- `uploads` / `exports`: the kind, so one user's uploads and exports list separately.
- `{YYYY}/{MM}/{DD}`: the date, so one user's files for a day or month are a prefix, and the listing is sorted by it.
- `{uuid}`: generated by my code, so no two files can collide and the name tells you nothing about the content.
- `.{ext}`: kept from the upload so the file still opens, and checked against an allow-list.

This makes "everything for user X" cheap (one list call on `users/X/`), and also "user X's uploads" (`users/X/uploads/`). It does not make "everything uploaded last Tuesday" cheap, because the date comes after the user, so I would have to list every user's prefix and filter on the date (O(n) in the number of users). I chose this because my app's common question is "what are my files", and a whole-bucket by-date query is a rare admin or cleanup job that a sweep can afford.

Two users both upload `resume.pdf`:
- User 17: `users/17/uploads/2026/10/05/3f1c9e0a-6b2d-4c71-9a55-0d8e7f1b2c34.pdf`
- User 42: `users/42/uploads/2026/10/05/b7a4d2e8-1c93-4f06-8e2a-5c6d9b0f3a11.pdf`

They differ in `{user_id}` and `{uuid}`, which neither user chose, and the name `resume.pdf` is not in the key at all (it is kept in metadata). The second upload cannot replace the first.

Never put a secret in a key, such as an email, a password-reset token or an API key. Keys show up in logs, listings and signed URLs, and an unguessable key is not access control.

### 1.2 Content Types
I would prefer using the linux `file` tool, and with the `--keep-going` flag when possible. 
What this really is: Byte sniffing
The file tool looks at the bytes to decide what type of file it is, so a file cannot just rename itself to pass. The `--keep-going` flag makes it keep listing every type it matches instead of stopping at the first one, so I can reject a file that looks like more than one thing (for example an image with something else hidden in it).

The content type I store comes from my allow-list after this check, never from the client's claim. A security problem happens when the stored type is `text/html`: if that object is later served from a presigned URL, the browser renders it and runs any script inside it, which is stored cross-site scripting on my storage URL. I would store `text/plain` or `application/octet-stream` instead (optionally with `Content-Disposition: attachment`), so the browser downloads it and doesn't run it.

No compressed files should ever be allowed. In most cases for my group's lost and found app, we would allow allow 2-4 image file formats and ANYTHING else should be denied on the spot.

### 1.3 Upload flow
Participants: the browser, my API, and the object store.
1. Browser to API: `POST /files/presign?filename=photo.png` (a short request, about 100 bytes).
2. API to itself: checks the extension, generates the key, and signs the URL locally. This makes no call to the store.
3. API to browser: `201` with the key and the signed PUT URL (about 600 bytes).
4. Browser to store: `PUT` of the 2 GB file directly to the signed URL.
5. Store to browser: `200` (or an error). My API is never told.

The only bytes that cross my API are steps 1 and 3, about **1 KB** in total. The 2 GB goes straight between the browser and the store. The only backend work is the extension check, the key creation and the local signing.

Two failure points after my API has already responded:
- **The upload fails part-way** (connection drops, tab closes). The store returns an error, or the browser just stops. The user sees a failed or stalled upload, and my API never knows. There may be no object, or incomplete parts left behind.
- **The URL expires** (the user takes too long, or waits before starting). The store returns `403`, and the user sees an upload error and has to ask for a new URL. My API never knows.

I would go with a completion callback because it is cheap. It misses the case where the user closes their browser before the POST is done.

### 1.4 Index and store

The metadata approach can't be searched or filtered. You can't ask questions about things only in metadata, because the store cannot query metadata. The only thing I can do is list keys by prefix, so finding a file by its original name means listing every key and reading each object's metadata one at a time.

Tutorial lines:
- From 4.1: "metadata is not searchable: there is no query but list-by-prefix."
- From 4.2: `list_files` "issues one `head_object` per key — the concrete reason 4.1 says production keeps an index."

Orphan object: An object in the store that nothing tracks. It has no row in my database to describe it or point to it, so it takes up storage nobody can reach. This happens when I write the object first and then the row fails.
Orphan row: A row that points to an object that doesn't exist, so my API would hand out a URL that returns 404. This happens when I write the row first and then the object fails.
I would rather have orphan objects, because users never see them, and a sweep can find and clean them up later.

### 1.5 Two workloads
Profile photos: standard (hot) storage. They are read constantly and uploaded pretty frequently, so I need fast response times. A colder class would also hurt here: each photo is under 1 MB, and there are 100,000 of them, so a colder class's per-object overhead and minimum billable size would be charged on every one, and its minimum billable duration (30, 90 or 180 days) would be charged on any photo that gets replaced. Numbers I would look up: the price per GB for each class, the per-object overhead or minimum billable size, the minimum duration, and the retrieval fee.
Backups: a cold or archive class. They are 1-10 GB each, read about once a year and kept seven years, so the minimum billable duration doesn't matter because I'm easily exceeding it, and the per-object overhead is tiny next to files this large. Cost is the only concern, so I want the lowest price per GB. Numbers I would look up: the archive price per GB-month, the retrieval fee and time, and the minimum billable duration.

What makes the difference: the same rule sends them opposite ways because cold storage pays off for objects that are large, few and long-lived, and loses money on objects that are small, numerous or read often.

# Part 3

### 3.1–3.4 storage_report.py
I wrote `mystore/storage_report.py`. It imports `Store` from `store.py`, so the endpoint, bucket, region and credentials all come from the environment, and it names no provider. `--prefix` is optional. I use `list(store.list(prefix))` to consume the generator, which already paginates.
- **Unstamped:** I call `head()` on every key and flag it if `original-name` is missing from the metadata.
- **Off-scheme:** I check each key with `re.fullmatch` against `(uploads|direct)/YYYY/MM/DD/<uuid>.<ext>`.
- **Bytes by prefix:** I sum sizes by the first part of the key and print a grand total.
- **Exit codes:** 0 for clean, 1 if either class is found, 2 if it could not run. Reaching the store fails with `EndpointConnectionError`, which I catch and print to stderr, so an unreachable store is never reported as a clean bucket. I tested this by pointing `S3_ENDPOINT` at `http://nowhere:9000` and got `exit=2`.

**Clean run** (`report_clean.txt`): I uploaded 3 files through `POST /files`. The report found 0 unstamped and 0 off-scheme (`uploads: 29` bytes) and printed `exit=0`.
**Dirty run** (`report_dirty.txt`): I added a presigned-PUT object (`put=200`) and an object at `stray/oops.txt`. The report found the `direct/...png` object unstamped, and `stray/oops.txt` both unstamped and off-scheme. It printed `exit=1`. The stray key is in both lists because I never gave it metadata.

### 3.5 Lifecycle proposal
1. **Abort incomplete multipart uploads after 3 days.** An upload that starts and never finishes leaves billed parts that appear in no object listing. 3 days is long enough for a slow connection to retry a large upload, and short enough that abandoned parts don't pile up.
2. **Expire non-current versions after 30 days.** Versioning protects against my own `DELETE` or an overwrite, but without an expiry rule every old version is kept and billed forever. 30 days gives time to notice and recover a mistake.
